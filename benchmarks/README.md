# Measure full API speed

These tools measure the Python, R, and JavaScript APIs. They keep the runtime code unchanged. See `PROTOCOL.md` for the driver interface and `../docs/plans/clique-performance/design.md` for the accepted design.

Install the Python package dependencies and `benchmarks/requirements.txt` in one environment. Install the R package dependencies plus `jsonlite`, `microbenchmark`, and `digest`. The R clock requires `microbenchmark`. Run `npm ci` and `npm run build` in `js/` in each source checkout. Use clean Git worktrees. The harness binds source commits, executable JavaScript files, lock files, and dependency versions. It compares JavaScript output with a fresh temporary build. It hashes the installed solver and compiler files. Version records declare the solver settings. Profiles read the settings from actual solver calls.

All output paths must be outside the harness checkout. Manifest, freeze, and audit commands require a new output file. They do not replace existing evidence. Keep the baseline checkout at its exact commit. Run each command from the same clean harness checkout. The example uses absolute paths supplied by the operator:

```sh
python benchmarks/run.py manifest --repo "$baseline_repo" --output "$evidence_dir/inputs.json"
python benchmarks/run.py profile --repo "$baseline_repo" --manifest "$evidence_dir/inputs.json" --output "$evidence_dir/baseline-profiles"
python benchmarks/run.py pilot --repo "$baseline_repo" --manifest "$evidence_dir/inputs.json" --output "$evidence_dir/pilot"
python benchmarks/run.py capture --repo "$baseline_repo" --manifest "$evidence_dir/pilot/manifest.json" --output "$evidence_dir/baseline-capture"
python benchmarks/run.py compare --kind calibration --run-id calibration-1 --baseline "$baseline_repo" --candidate "$baseline_repo" --manifest "$evidence_dir/pilot/manifest.json" --output "$evidence_dir/calibration"
```

Review the profiles before selecting a runtime change. The current `freeze` command supports the essential cover certificate candidate. It selects every solve case where the essential decisions cover the graph and solver adapter calls use at least 25 percent of the profiled full API time after measured probe cost is removed. The ratio is `metrics.solver_total_ns / (phases_ns.total - metrics.probe_ns)`. The solver total already excludes these probes. Each declared language and method target needs five development cases and five validation cases. An unsupported candidate needs its own reviewed eligibility rule before timing.

```sh
python benchmarks/run.py freeze --pilot "$evidence_dir/pilot" --manifest "$evidence_dir/pilot/manifest.json" --profiles "$evidence_dir/baseline-profiles" --capture "$evidence_dir/baseline-capture" --calibration "$evidence_dir/calibration" --output "$evidence_dir/frozen.json"
```

Calibration compares the same source to itself. Each case's 95 percent interval must stay between 1/1.05 and 1.05. Freeze also checks this band for every complete eligible target group. This rejects large false gains as well as large slowdowns. Set the sampling design before candidate timing. If calibration is inconclusive, increase the baseline sampling effort and repeat calibration. The harness permits at most 16 process pairs and 36 measured batches. A larger design requires a separate documented change before candidate timing. Keep the graph inputs fixed. Do not adjust the design after candidate results are known.

After the candidate passes its correctness suites, capture its actual decisions and resource outcomes. Run the two timing comparisons in sequence on an otherwise idle host. Keep other test and build jobs stopped during these runs.

```sh
python benchmarks/run.py capture --repo "$candidate_repo" --manifest "$evidence_dir/frozen.json" --output "$evidence_dir/candidate-capture"
python benchmarks/run.py profile --repo "$candidate_repo" --manifest "$evidence_dir/frozen.json" --output "$evidence_dir/candidate-profiles"
python benchmarks/run.py compare --kind candidate --run-id candidate-1 --baseline "$baseline_repo" --candidate "$candidate_repo" --manifest "$evidence_dir/frozen.json" --output "$evidence_dir/candidate-1"
python benchmarks/run.py compare --kind candidate --run-id candidate-2 --baseline "$baseline_repo" --candidate "$candidate_repo" --manifest "$evidence_dir/frozen.json" --output "$evidence_dir/candidate-2"
python benchmarks/run.py audit --pilot "$evidence_dir/pilot" --calibration "$evidence_dir/calibration" --manifest "$evidence_dir/frozen.json" --runs "$evidence_dir/candidate-1" "$evidence_dir/candidate-2" --baseline-capture "$evidence_dir/baseline-capture" --candidate-capture "$evidence_dir/candidate-capture" --baseline-profiles "$evidence_dir/baseline-profiles" --candidate-profiles "$evidence_dir/candidate-profiles" --output "$evidence_dir/acceptance.json"
```

Freeze and final audit require the raw pilot directory. Keep its input manifest, selected manifest, first and warm responses, metadata, and process receipts. The checks derive each batch length again from the recorded warm call. They reject missing receipts and changed source, harness, or dependency records.

The pilot prints each failure with its exact resource class and error. An unsupported error or process close failure stops the pilot. Before freeze, capture stops if a case listed as a pilot failure succeeds. Keep the raw evidence and start a new pilot before calibration. A candidate capture marks any completion of a listed baseline failure. The final audit still requires independent correctness evidence for that result.

The final audit reads raw pilot, calibration, and candidate evidence again. Every successful calibrated case needs a raw response pair for each process. Every measured batch must have the same full result hash as that pair and the baseline capture. The audit checks that calibration ended before candidate timing. It checks the measurement code, sampling design, and complete eligible target groups. One timing run cannot establish acceptance. Each target must show a geometric mean ratio of at most 0.90. Its 95 percent upper confidence bound must be below 1. Each case's upper bound must be at most 1.05. Inclusive thresholds allow four machine epsilon units for floating point roundoff. The target upper bound must still be strictly below 1. Both independent runs must pass. Correctness and resource failures block acceptance. The acceptance report records the audit harness source before and after validation. A dirty or changed audit harness blocks acceptance.

The process guard supports macOS and Linux. The default memory bound is 8,192 MiB. The harness samples the guard and its live descendants. After each driver exits, an OS wait4 receipt records the driver lifetime peak RSS. The audit checks both values. This is not a kernel memory ceiling. The native receipt does not measure the peak of a whole process tree at one instant. It does not cover detached or unwaited descendants. Missing receipts block acceptance. Rare PID reuse within one collection also blocks acceptance and requires a new collection. The audit records RSS at every response and compares growth from the first to the last measured response in each process. Candidate growth must not exceed baseline growth by more than the predeclared 32 MiB allowance. This allowance does not raise the absolute memory limit.

Freeze binds the measurement and acceptance code to the calibration code. This includes the case generator, analysis, drivers, process guard, and outcome validators. It checks the full code binding and machine records for every profile, capture, pilot, and comparison stage. Frozen capture, profile, and candidate timing commands check the executing code before a driver starts. Final audit checks every recorded collection against the frozen code. A later runtime, test, or document commit can pass if these bound files are unchanged.

Each timing process runs three warmup batches, then nine or more measured batches. Pair order is random with equal counts where possible. An odd surplus alternates across processes. Analysis verifies each stored pair order against the seeded schedule, including the random draws used for warmups. The default design uses eight fresh process pairs. The baseline pilot sets iterations to reach about 50 milliseconds per batch. The estimator takes a median across batches within each process, then a median across processes. The bootstrap resamples paired batches within each original process before it resamples the resulting process values. It uses the same draws across target cases.

Module and solver load costs appear in version records. The R driver executes repository source through `Rscript` in a private environment. It does not load an installed reducer package. Its module load record covers source evaluation and Matrix loading. Its clock reports observed initialization and resolution warnings. Elapsed values use the clock's nanosecond scale. They do not establish absolute timing calibration.

The pilot records the first full API call and warm calls separately. Profile hooks and result serialization are outside acceptance timing. The coordinator runs three warmup requests through the same profile path, then collects one eligibility profile. A profile also records one uninstrumented full call before hook setup. The profile wall limit covers the whole request, including both full calls. Preprocessing runs no full API call. The signed time difference includes probe cost and runtime noise. It is not subtracted from any measurement. Profile regions are inclusive and can overlap. Profile times choose candidate targets. They do not prove a speed gain.

The default corpus includes ordinary inputs and bounded stress inputs. The three part multipartite graph is the earlier `overlap9` case. Five part multipartite solves are opt in. Six to eight part cases stop after preprocessing. Nine parts must reach the existing clique limit. The tools enforce external wall limits. Memory polling and native peak receipts check the frozen memory bound with the coverage limits above. Baseline failures receive no speed ratio. Preprocessing failures have a separate map of exact case keys and resource classes. A candidate must preserve each successful baseline preprocessing result. A candidate that completes a previously failed preprocessing case gets an unscored preprocessing record. A new candidate success needs independent correctness evidence.

The `profile --include-opt-in` command keeps optional failures as diagnostic records. A profile file with an optional failure cannot enter frozen acceptance. Keep that file. Collect required profiles in a separate output directory without `--include-opt-in`. Do not delete rows or change old records. Successful optional profiles can enter frozen acceptance. Each row must match a manifest case. The candidate must provide the same profile coverage and results.

Shared CI checks harness logic and driver behavior. It has no elapsed time thresholds. The package archive checks keep these tools out of runtime packages.
